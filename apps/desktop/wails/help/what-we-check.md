# What Clear Signal checks, and what it does not

This is the list of every failure, warning and "not checked" outcome Clear Signal can report, and of the failures it cannot catch. Read it instead of guessing: if a failure is not here, we either do not catch it or we have forgotten to write it down, and in both cases we want to hear about it.

In the app this list is the **What We Check** tab of the Help panel (menu Help, What We Check); in the repository it is `apps/desktop/wails/help/what-we-check.md`.

Two kinds of checking, with the names the product uses:

- **API Contract Validation** (section 1): a response is compared with what the OpenAPI spec declares for it. It runs on every scenario step that has a spec, in `clrsig conform`, and for the `schema` assertion.
- **Spec Conformance Testing** (section 2): every operation of the spec is exercised, with requests built from the spec, and the run itself is checked (requests that could not be sent, negative probes, coverage, changes between two versions of a spec).

## How to read the tables

- **ID.** `CS-<AREA>-<number>`. These are provisional: backlog item B-049 will make them the IDs shown in every report, and will keep this file and the code in step with a test. Quote an ID when you report a problem.
- **State.** **caught**: we detect it. **partly**: we detect some cases (the note says which). **not caught**: we do not detect it. **not checked**: the outcome looks like a pass but nothing was compared (section 1.2).
- **Severity today.** Every failure below fails the run (exit code 1). The only exceptions are marked *warning* (shown, exit code unchanged) or *not a failure*. Separate warning levels are backlog item B-050.
- **Severity (levels).** Each check in `packages/core/checks` has a default level: *failure* (fails the run), *warning* (shown, counted, does not fail unless `--fail-on warning`) or *note* (information; the “not checked” rows). Reports show the level in JSON (`severity`), as `WARN` in text, HTML and Markdown, and as a passing JUnit case with the warning in its output. In this release every finding check is a failure.
- **Evidence.** The test (or the Conformance Server operation) that proves the row. A row without evidence is at most *partly*. Rows marked **KnownGap** are pinned by a test of the same name, so when the behaviour changes the test fails and this file must change with it.
- **Two checkers.** The response checks exist twice. **A** is the step spec check (`validateSpec`) and `conform`, which call `ValidateResponseByPath`. **B** is the `schema` assertion (`type: schema`), which calls `ValidateResponse` by operation id. B is narrower: it only compares the body. A failed `schema` assertion in a scenario report carries the same check ID, why and fix as the same failure from `conform` (`checkId` in the JSON report), when the message is one the catalog recognises (`TestText_FailedSchemaAssertionCarriesACheckID`).

Every failure message follows the same shape: **what** is wrong, **where** it is (the part of the response and the place in the spec), **why** it fails and **how** to fix it. Use `clrsig conform --explain` to see it on screen; the JSON, HTML, Markdown and JUnit reports and the desktop page always show it.

### 1.2 Not checked: looks like a pass, nothing was compared

These never fail the run and never count as passing a check. Scenario results show the ones marked * as "not checked" with the reason.

| ID | Title | When it happens | Evidence |
|---|---|---|---|
| CS-NC-001 | Path not in the spec * | A scenario step calls a URL the spec does not describe: nothing to compare with. A server's base path (`servers: [{url: https://host/v1}]`) is removed before matching, so `/v1/users` matches `/users`; before 0.7.2 a spec with `servers` matched nothing and every response passed unchecked. | `TestCheck_NotChecked`, `TestRunner_SpecCheckStates` |
| CS-NC-002 | No response content declared | The spec declares the status but no body (`204`, or a description only): any body is accepted. | `TestCheck_NotChecked` |
| CS-NC-003 | Binary or schema-less media type | `application/octet-stream` and similar: there is no structure to compare. | `TestCheck_NotChecked`, `TestCheck_ResponseMediaTypes` |
| CS-NC-004 | Spec validation turned off for the step * | The step has `validateSpec: false`. | `TestRunner_SpecCheckStates` |
| CS-NC-005 | Scenario has no spec | No `specFile`, so no response check runs at all. | `TestRunner_NoSpecLeavesSpecCheckEmpty` |
| CS-NC-006 | The step did not complete * | The request failed before a response arrived (network error). | `TestRunner_SpecCheckStates` |
| CS-NC-007 | Operation skipped by a filter or read-only | `--tags`, `--paths`, `--changed-against` (an operation no change touched) or `--read-only` left it out: not sent, shown as skipped, counted as not covered. | `TestRunner_Run_TagFilter`, `TestRunConformance_ReadOnlySendsNoWrites`, `TestConformReadOnlySendsNoWrites` |
| CS-NC-008 | Response without a Content-Type | A body with no `Content-Type` header is read as JSON (lenient), not reported. | `TestCheck_ResponseMediaTypes` |
| CS-NC-009 | Declared media type without a decoder | The spec declares `application/xml`, `text/csv` or another type the validator cannot read: the body is not compared with the schema and nothing is reported. Status, headers and Content-Type are still checked. Only `application/json` and `+json` types are read as one JSON document: `application/x-ndjson` (one JSON value per line) and `application/json-seq` are not parsed as one, so a correct stream is not reported as invalid JSON. An example for such a type in the spec (an XML string) is not checked against the JSON schema either, so the document loads. | `TestCheck_ResponseBodyFormat` `TestConform_NDJSONIsNotOneDocument`, `TestParse_AcceptsAnExampleForANonJSONMediaType` |

### 2.2 Negative probes (`clrsig conform --negative`)

Each probe sends a deliberately wrong request and **passes when the server answers any 4xx**. A probe fails when the server accepts the bad request (or answers anything else outside 4xx). The codes named in the rows below are what a correct server is expected to send; they are **not enforced** (CS-GAP-012).

| ID | Title | What is sent | State | Evidence |
|---|---|---|---|---|
| CS-PROBE-001 | Missing required field accepted | A body without one required field (expected `400` or `422`). For a `oneOf` or `anyOf` body every branch is probed with its own required fields. | caught | `TestGenerateNegativeProbes_ExpectedKinds`, `TestNegativeRunner_LenientServer_ProbesFail`, `TestProbes_EveryOneOfBranchIsProbed` |
| CS-PROBE-002 | Wrong field type accepted | A body with one field of the wrong type (expected `400` or `422`). | caught | same |
| CS-PROBE-003 | Missing required query parameter or header accepted | A request without a required query parameter or header (expected a `4xx`). | caught | same, `TestProbes_MissingRequiredHeader` |
| CS-PROBE-004 | Missing credentials accepted | A request to a secured operation without credentials (not probed when authentication is optional; the credential is removed wherever the spec puts it: the `Authorization` header, an API-key header, query parameter or cookie) (expected `401` or `403`). | caught | same, `TestNegativeRunner_StrictServer_AllPass`, `TestProbes_NoCredentialsDropsACookieAPIKey` |
| CS-PROBE-005 | Probes follow the filters and reach the machine-readable reports | `--tags` and `--paths` limit the probes to the selected operations (before 0.7.3 every probe of the spec ran), and the JSON report (`probes`) and the JUnit report (one test case per probe) list the probes; a failed probe fails them as it does the exit code. A `--paths` prefix selects the same operations and probes whether a parameter is written as in the spec (`/items/{id}`) or as generated (`/items/{{id}}`); up to 0.13.0 operations took only the second spelling and probes only the first, so one side silently selected nothing. | caught | `TestNegativeRunner_FiltersLimitTheProbes`, `TestReports_CarryTheNegativeProbes`, `TestPathsFilter_BothSpellingsSelectTheSameOperationsAndProbes` |
| CS-PROBE-006 | A probe got no answer | When the server does not answer a probe (connection refused, timeout) the probe is `ERR`, counts as a failure, and the summary line says `FAILED` (it used to say `PASSED` next to `0 passed`). | `--negative` with no server running. | caught | failure | `TestNegativeText_ErroredProbesAreNotPassed` |

Only these four kinds are probed. Wrong header or path-parameter types, boundary values, enum violations, unknown fields and bad credentials (as opposed to none) are **not** probed (CS-GAP-009).

### 2.5 The spec itself (`clrsig validate --spec`, Check Conformance)

A response check blames the server for what the spec got wrong, so these are worth fixing first. The OpenAPI parser already refuses a spec with a duplicate `operationId` or an undeclared path parameter (the spec does not load), so only what it accepts is listed here.

| ID | Title | What it means | Example | State | Severity today | Evidence |
|---|---|---|---|---|---|---|
| CS-SPEC-001 | Operation without an operationId | Reports, coverage and the `schema` assertion name operations by `operationId`; without one they fall back to the method and path. | `GET /things` with no `operationId`. | caught | warning | `TestLint_FindsWhatIsWrongWithTheDocument` |
| CS-SPEC-002 | Required property that is not declared | A schema lists a name under `required` that is not among its declared `properties` (and the schema does not compose others or allow additional properties), so a response can never satisfy it, or it is never checked. Nested schemas, request bodies and responses are walked. | `required: [id, email]` with only `id` declared. | caught | failure | `TestLint_FindsWhatIsWrongWithTheDocument`, `TestLint_ASchemaThatComposesIsNotJudged` |
| CS-SPEC-003 | Example that breaks its own format | An `example` that does not match an `email`, `uuid`, `ipv4` or `ipv6` format. The spec still loads, but none of its examples are checked. | `format: uuid` with `example: "123"`. | caught | warning | `TestLint_AnExampleThatBreaksItsFormatIsReported`, `TestFormats_ABadFormatExampleDoesNotRefuseTheSpec` |

## 3. Known gaps: what we do not catch

| ID | Title | What is missed | Why | Evidence |
|---|---|---|---|---|
| CS-GAP-001 | Formats outside the supported list | `format: uri`, `hostname`, `duration` and any other format that is not `date`, `date-time`, `email`, `uuid`, `ipv4`, `ipv6` or `byte` are accepted without a check (the OpenAPI specification allows unknown formats): `"link": "not a uri"` passes. | These formats are the ones with the least risk of reporting a correct server; the URL-like ones are added after a trial on real specs. | `TestCheck_ResponseBody` (**KnownGap** row), `TestFormats_EachSupportedFormat` |
| CS-GAP-002 | Extra properties on open schemas | See CS-RESP-010: not a violation under the OpenAPI default. A strict mode could warn about them. | By design of OpenAPI; a warning level (B-050) would be the place. | `TestCheck_ResponseBody` (**KnownGap**) |
| CS-GAP-003 | Undeclared response headers | A header the spec does not mention is never reported. | Not implemented; low value until warnings exist (B-050). | `TestCheck_ResponseHeaders` (**KnownGap**) |
| CS-GAP-004 | Non-JSON response bodies | XML and other media types are not validated (CS-NC-009). Status, headers and the Content-Type are still checked. | No decoder for them. | `TestCheck_ResponseBodyFormat` |
| CS-GAP-005 | Response-time trends | `conform --max-response-time` (CS-RESP-014) and the scenario `duration` assertion fail a response over one limit, and the Contracts store records each operation's last and slowest response time (shown on the Contracts page and in its exports). A different limit for the operations under a path prefix is set with `--max-response-time-for` (CS-RESP-014). Nothing fails on a trend (a response that is getting slower but is still under the limit). | Trends are a non-goal of the proposal `docs/enhancements/2026-11-22-response-time-assertions.md`. | `TestDuration_AssertionComparesResponseTime`, `TestScenarioCoverage_RecordsResponseTimes` |
| CS-GAP-006 | XML request bodies | Operations that take an XML (or other non-JSON, non-form) body are generated **without** a body. JSON, `application/x-www-form-urlencoded` and `multipart/form-data` bodies are generated (CS-REQ-003). | Only those three families are generated. | `TestCheck_XMLRequestBodiesAreNotGenerated_KnownGap` |
| CS-GAP-008 | Security beyond "no credentials" | Wrong, expired or under-privileged credentials are not probed; only their absence is (CS-PROBE-004). | Not implemented. | no check exists |
| CS-GAP-009 | More negative probes | Wrong header or path-parameter types, boundary values, enum violations, unknown fields. | Not implemented; only four kinds are generated. | `TestGenerateNegativeProbes_ExpectedKinds` |
| CS-GAP-010 | Callbacks, webhooks and links | Operations that are not under `paths` are not exercised. | Only `paths` are generated. | no check exists |
| CS-GAP-012 | A probe rejected for another reason | A probe passes on **any** `4xx`. A `401`, `404` or `429` answer to a body with a missing or wrong field passes CS-PROBE-001 or CS-PROBE-002, although the server may never have validated the body (a login rejects the credentials first, a rate limit answers before anything is read). The same applies to a `404` where CS-PROBE-004 expects `401` or `403`. Read the status printed beside a passing probe. | Any `4xx` was chosen so that a correct server with its own choice of code is not failed; telling the reasons apart needs a new outcome. | `TestNegativeProbe_AnyClientErrorPasses_KnownGap` |
| CS-GAP-013 | An empty value counts as a value outside the path and the credentials | In the requests `conform` builds, an empty value **in the path or in a credential** makes the operation "not sent" (CS-RUN-001). Anywhere else, a variable that is defined but empty (`value: ""`) fills its placeholder with nothing and the request **is sent**: a required query parameter, header, cookie parameter or body value goes out empty, and so does an empty basic password. In a scenario (`run`), every defined value counts, empty or not. A declared error status in the answer can then show as passing. | Empty can be what is meant there (an empty filter, a key sent as the basic user name with no password, a scenario that tests a missing credential). | `TestRun_AnEmptyValueElsewhereIsSentAsEmpty_KnownGap` |
| CS-GAP-017 | A secret that nothing marks as one can still be quoted | What a report quotes from a response is limited by rules about names and shapes (CS-RUN-011). A secret in a field with an ordinary name, too short or too plain to look like a token, **is** quoted when it is itself the value that broke the spec; so is personal data in that position. An error body's excerpt masks credential names, token-like texts and e-mail addresses, not other free text. Passwords are masked only when written in a way CS-RUN-011 lists. **Not** masked, for example: `user:password@host` without a scheme; `password: x` or `"password":"x"` written inside a text; other names (`pass=`, `pw=`); command-line options (`--password x`); percent-encoded query strings; what follows a space in an unquoted value (`Password=two words`); an address whose password holds an unencoded `/`, `?`, `#` or space; and a fragment of a password a scenario expects (`contains app:secret@`). Baseline files written by earlier versions are not rewritten and can still hold what they recorded. | A report must say what was wrong. Name fields that hold secrets accordingly, and treat reports of sensitive operations with care. | `TestConform_AnUnrecognisableSecretThatBreaksTheSpecIsQuoted_KnownGap`, `TestCredentials_UnmarkedWaysOfWritingAPasswordAreQuoted_KnownGap` |
| CS-GAP-019 | A baseline cannot follow a value that changes inside the message (OpenAPI 3.1) | Some 3.1 messages hold the failing value (a `pattern` or `format` failure: `'ab-one' does not match pattern …`). When the value differs on each run (an id, a time), the violation differs too, so a recorded one is reported as new, and the old entry as fixed. The run fails; nothing is hidden. | Fix the violation, or leave the operation out with `--paths` or `--tags`. | `TestBaseline_AChangingValueInsideTheSentenceIsNewEachTime_KnownGap` |
| CS-GAP-016 | A declared error answer passes | An operation conforms when the answer matches what the spec declares **for the status the server gave**. `GET /users/{id}` with an id that does not exist passes as `PASS … 404` when the spec declares a `404`, although the successful answer was never seen. | By design of conformance: the answer is one the spec allows. Read the status codes and give values that exist. | `TestConform_ADeclaredErrorAnswerPasses_KnownGap` |
| CS-GAP-011 | Only the first problem per response | A response with a header problem and a body problem reports the header problem first. | The validation library stops at the first problem. | `TestResponseChecks` |

## Adding to this list

Whenever we learn of a failure kind, a case we do not catch, a false pass or a false failure, add a row here in the same change: ID, title, what it means, example, state and the test that proves it. When a gap is fixed, move its row to the checks and update its test. A test (`TestCatalogCitesRealTests`) fails if a row cites a test that does not exist.
