# Pre-release check — 2026-11-21

Last check before tagging **v0.6.0**, since `check-2026-11-20.md`. Scope: what was fixed since that report (B-052, B-056, B-057, B-059, B-060, B-062, B-066), the new **Workspace page** (B-055: `packages/core/workspaceinfo`, `DashboardService`, `WorkspaceTab`), the commits after the "prepare v0.6.0" commit, and the release pipeline.

Method: `go vet`, `gofmt -l`, `go test` for all three Go modules, frontend `tsc` and vitest, real-binary runs of `clrsig conform` against a closed port and against a small live server (with a required query parameter, a required header and an XML response), and a read of the new dashboard code, `release.yml`, `ci.yml`, the `Dockerfile` and `action.yml`.

Not run: Playwright browser tests, the desktop app itself (no GUI session), the release workflow. Findings about the Workspace page come from reading the code and its tests.

## New findings

| # | Finding | Severity | Suggestion |
|---|---|---|---|
| R1 | **The Docker image reports the wrong version.** The `Dockerfile` builds with `-ldflags="-s -w"` and no `-X main.version=…`, and the release workflow passes no build argument, so `docker run ghcr.io/fuvito/api-workbench:v0.6.0 --version` prints `dev`. The release process (section 4, Docker) tells you to confirm it prints the new version, so that step will fail on every release. Not new to 0.6.0. | Medium | Add `ARG VERSION=dev` and `-X main.version=${VERSION}` to the `Dockerfile`, and `build-args: VERSION=${{ github.ref_name }}` to the `docker/build-push-action` step. |
| R2 | **The release workflow installs `wails@latest`** in three jobs, while the app is held at v2.17.1 (`go.mod`, backlog B-016). A new Wails release can change the build or the generated bindings between the last green CI and the tag, and the release is the first place it would show. | Low–Medium | Pin it: `go install github.com/wailsapp/wails/v2/cmd/wails@v2.17.1` in the three jobs. |
| R3 | **The Workspace page can show a coverage total for the wrong spec, or none.** Coverage is stored under the spec path *as the scenario wrote it* (`accumulateCoverage(..., sc.SpecFile, ...)`), but `workspaceinfo` merges specs by the *resolved file* and keeps only the first scenario's spelling. Two scenarios in different folders that name the same file differently (`../specs/a.yaml` and `../../specs/a.yaml`, or one absolute) give one row that carries only the first spelling's coverage, and the other spelling's totals and its "failed the last time" warning are never shown. The same row also reuses one `ref` as the React `key`, so two different files that are written identically relative to different folders produce duplicate keys. | Low–Medium | Look coverage up by every spelling that resolves to the file (keep a list of refs in `Spec`), and key rows by resolved path. |
| R4 | **The "Needs attention" list can go stale.** The page re-reads when the workspace changes, after a scenario run, after a coverage refresh and when the environment changes; saving a scenario or an environment's values does not refresh it. After fixing a flagged scenario the card stays until the user presses Refresh. I could not confirm whether the tab is remounted when you switch back to it. | Low | Bump the refresh trigger on scenario and request save, or reload when the Workspace tab becomes active. |
| R5 | **No warning for a placeholder the selected environment does not define.** The "No environment is selected" card lists unresolved `{{names}}`, but once any environment is chosen the check stops. A scenario that uses `{{token}}` against an environment that has no `token` shows "Nothing needs attention" and then fails at run time. The same data is already there (`unresolved` set and the environment's variable names). | Low–Medium (the page's purpose is to say this before a run) | Run the same comparison against the selected environment's variables and report the difference as a card. |
| R6 | **The unresolved-placeholder scan reads the whole scenario file as text.** `{{name}}` inside `notes`, `label` or a description counts as a use, and placeholders inside the `requestRef` files a step points at are not looked at. It can both invent and miss names. | Low | Scan only the places that are sent (URL, headers, query, auth, body, assertions) after parsing, and follow `requestRef`. |
| R7 | **`DeleteFolder` is not restricted when no workspace is open** (the check is skipped when `workspacePath` is empty), and it ignores hidden entries when deciding a folder is empty, then calls `RemoveAll`, so a folder that holds only `.git` is deleted with its contents. Reachable only through a crafted call, since the UI offers it from the request tree. Also `strings.HasPrefix(rel, "..")` in these path guards rejects legitimate names that start with two dots. Same family as the earlier finding 10 (B-064). | Low | Refuse when no workspace is open, refuse folders that contain any hidden directory, compare `rel == ".."` or `".."+separator`. |
| R8 | **`workspaceinfo.within` is lexical.** A spec reached through a symlink inside the workspace that points elsewhere is shown as "found", not "outside". The spec is read from the real location. | Info | Resolve with `filepath.EvalSymlinks` before comparing, if "outside the workspace" is meant strictly. |
| R9 | **The open-workspace reminder returns every time the Workspace tab is reopened.** "Dismissed" lives in component state only. | Info | Remember the dismissal per workspace for the session. |

## Verified, no change needed

- **The Workspace page never carries a value.** `DashEnvVarIO` has name, secret flag, set flag and the name of the unset process variable, nothing else; the attention texts name variables, not values.
- **It only reads.** `Inspect` and `GetWorkspaceOverview` open files and stores read-only; the spec and request-reference checks never fetch a URL.
- **Temporary workspaces** are not remembered, are labelled, and have their own close reminder.
- **Placeholders `{{$function}}`** are not mistaken for undefined variables (the pattern starts at a letter).
- **`conform --negative --coverage`** end to end against a live server: operations pass, a lenient server correctly fails the "missing required query parameter" probe, coverage 2 of 2.
- **Release notes and version.** `AboutDialog.tsx` (`Version 0.6.0`, notes include the Workspace page), `user-guide.md` and the two version tests agree.
- **The CLI version comes from the tag** (`-X main.version`), and the Windows installer takes it from `iscc /DMyAppVersion`.
- **Tracked bindings.** `wailsjs/go/main/DashboardService.*` and `wailsjs/runtime` are tracked, so the frontend builds in CI before any `wails` command has run.
- **Working tree is clean.**
